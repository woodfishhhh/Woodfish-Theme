# Woodfish (monorepo)

**Type**: npm workspaces monorepo, TypeScript
**Products**: VS Code extension (`apps/vscode-extension`, published as `zhongjun.woodfish-theme`); official native DeepSeek Harness (dsh) plugin (`apps/dsh-web/plugin`, published as `woodfish-dsh-plugin`); `woodfish` desktop CLI for the Codex app and dsh native plugin installation/management (`apps/cli`), shipped three ways from one `woodfish.js`: npm package `woodfish`, `woodfish.exe` on the GitHub Release, and inside the VSIX (「为 Codex 启用 Woodfish」)
**Shared packages**: `@woodfish/theme-core` (pure color/effect core), `@woodfish/renderer-runtime` (in-page engines, effect plugin host), `@woodfish/chatgpt-app` (Codex selectors, CSS, overlay), `@woodfish/dsh-web` (dsh native dual-face plugin: host, client settings panel, intrusive renderer overlay), `@woodfish/effects` (shipped effect plugins and the Node side of the user's effects folder)

## Conventions

- **TypeScript strict mode** - no `any`, no `@ts-ignore`
- **Chinese UI** - all user-facing strings in Chinese
- **Workspace output to `out/`** - the VSIX package itself goes to the ignored repository-level `dist/`; other build outputs stay in their workspace `out/`
- **Runtime injection** - patches `workbench.html` through `workbenchPatcher.ts`
- **Core stays host-agnostic** - `packages/theme-core` must not import `vscode`, Electron, DOM or Node APIs
- **Generated files are committed** - regenerate with `pnpm themes:generate` / `pnpm runtime:build`
- **Two kinds of text gradients** - the 5 built-in themes use hand-tuned presets (`packages/theme-core/src/palettes/gradientPresets.ts`, keyed by token color); any other theme, and colors a preset does not list, use the derivation in `gradient/tokenGradient.ts`, which is modeled on the presets. Hosts pass background / foreground / preset through the engine's `gradientContext`
- **Bundled popular themes are unmodified upstream files** - `themes/<slug>/` holds the upstream JSON (VS Code reads JSONC; `scripts/lib/jsonc.js` parses it the same way), its `LICENSE.txt`, a `NOTICE.md` and Woodfish's own `theme.meta.json` (accents, tab gradient, cursor colors picked from the theme's palette). Only MIT-style licenses; list each in both THIRD_PARTY_NOTICES files. Add the slug to `port-palettes.js`, `package.json` and `themeRegistry.ts`, then `pnpm themes:generate`. They have no hand-tuned preset; gradients are derived
- **Codex effects are designed** - the owner wants Codex to look designed: rainbow reply text (pure CSS so streaming and long threads cost nothing), the selected sidebar thread copies the Bifrost console's 「创建 Key」 bridge button (owner's company, copying approved 2026-11-14: 1.5px seven-band conic ring turning every 3.2 s, navy face, blur(14px) halo; running threads a weaker halo; replaced the earlier playground #8 ring), Codex's caret defaults to 6px, solid, smooth 80 ms, Woodfish rainbow, no glow (the same as Woodfish's VS Code caret), the caret trail copies the VS Code Animations extension (MIT; single-color band, length 12, default `#ffffff`); the owner wants only the text caret's trail: the mouse trail was removed from Codex and VS Code in 8.1.1 (2026-11-14, “没有意义”), do not bring it back, streaming default is playground #1 (`docs/playground/streaming-text.html`: rainbow cursor at the end of the text + caret trail + 120 ms fade-in). Let the owner pick visual flourishes in a static playground like those. Judge on real Codex screenshots with the window in front (an occluded Codex is marked hidden and throttles frames, so `PrintWindow` captures go stale; CDP `Page.captureScreenshot` is reliable for page content)
- **Effects are plugins (the owner's core selling point)** - every visual effect is a folder (`effect.json` schema + `params.json` values + `effect.js` + `README.md`) shipped from `packages/effects/builtin/` into `%APPDATA%\Woodfish\effects` (shared by the CLI and the VS Code extension; `.woodfish-shipped.json` records what was shipped so upgrades only replace untouched files, `params.json` is never shipped, deleted folders stay deleted; bump `version` in `effect.json` when changing a shipped effect). A user tells Codex/Claude "改一下出字的粒子" and the AI follows the folder's `AGENTS.md`, which says: `user.css` first, then `params.json`, code last. `user.css` (effects folder root, shipped as a commented template, kept once edited) is mounted in `<body>` after every stylesheet in Codex and VS Code; every param is the CSS variable `--woodfish-<id>-<param>` and the effect host reads the computed `:root` values back into `ctx.params` and core values (`effectValuesFromCss` in theme-core), so canvas effects follow CSS too. Gradient colors that are not params are `var(--woodfish-<id>-<name>, default)` hooks in the effect CSS. The variable list is the effects folder's `README.md`; regenerate its param tables with `node packages/effects/scripts/css-variables.js` after changing an `effect.json` (a test checks it). Effects only talk to `ctx` (`renderer-runtime/effectHost.ts`): one shared canvas whose loop stops when idle and while the window is in the background, `ctx.onInsert` / `ctx.onCaret` / `ctx.onStreamEnd` fire for the user typing (Monaco in VS Code, the composer in Codex) and for Codex streaming a reply (`watchStream`, one flush per frame, no per-character DOM). A failing effect (syntax error with line, bad JSON, three runtime errors) is skipped and reported; the rest keep running. Values: Codex reads `params.json` (the settings page writes it through the watcher, `codex.json` keeps only palette, picture and custom CSS; an older `codex.json` is migrated once); VS Code reads `woodfishTheme.<camelId>.*` for its three effects (opt-in, default off) and `params.json` for any other. Reload: saving re-injects within ~250 ms; `woodfish reload` (touches `effects/.reload`, VS Code watches it too), Ctrl+Alt+R and 「刷新效果」 restart every effect. VS Code loads `effects.mjs` from global storage with `import()` (allowed under its CSP and Trusted Types) and polls `effects.json` every 1.5 s while focused
- **dsh is the third effect host (official native plugin, no user script)** - dsh (`dsh 0.2.2+`, both `dsh web` and `dsh desktop`) runs as an official dual-face native Cordis plugin `woodfish-dsh-plugin` built by `apps/dsh-web/scripts/build.js` into `apps/dsh-web/plugin/` (also embedded in `apps/cli/out/woodfish.js` for `woodfish dsh install`). The old Tampermonkey/Violentmonkey user-script path was completely deleted on 2026-11-25. Host half (`src/host/`): exports `name = 'woodfish-theme'` with 6 flat `.volatile()` string config fields persisted through `@deepseek-ai/dsh-settings` (`paletteDark`, `paletteLight`, `backgroundImage`, `customCss`, `userCss`, `effectsJson`), injects `window.__WOODFISH_DSH_BOOT__` via `webserver/index-inject`, and serves custom background uploads (`GET` and `POST ?action=upload|delete`, since dsh `ConnectionFetchMethod` only allows `GET`/`HEAD`/`POST`) stored under `$DSH_HOME/woodfish/backgrounds/`. Client half (`src/client/`): mounts a dedicated native Settings tab (`settings.section` id `woodfish`, plus `plugins.bundle.config`) where all 15 dark/light themes, custom backgrounds, `user.css`, and every single parameter of all 12 effects (73 controls total) adjust live and persist; syncs xterm and `theme-color` via `ctx.theme.overrideTokens('woodfish-theme', { '--woodfish-theme-sync': ... })` without writing inline `--dsw-*` tokens on `body`. Renderer (`src/renderer/`): runs the same effect plugins as Codex (`hosts` contains `dsh`), punches main/chat/right/code surfaces transparent over the background without clearing `--dsw-alias-bg-base`, and uses parameterized continuous (“Apple”) corners (`squircle-corners` `scale`/`shape`/`scanHardcoded`, plus `startNativeCorners()` mirroring dsh and builtin plugin CSS-module rules, cleanly releasing to 0 mirrored sheets when disabled). Note: `dsh 0.2.2-rc.5` CLI refuses `dsh plugin --profile desktop add` (Electron manages the desktop profile exclusively), so `woodfish dsh install --profile desktop` stages the bundle and instructs installation in dsh Desktop's Plugins Manager UI. Always verify on `dsh 0.2.2-rc.5` in an isolated temporary `DSH_HOME`, never the owner's own dsh config (`docs/hosts/dsh-web.md`)
- **Effect plugins must stay cheap** - measured 2026-11-14 in a real streaming reply: frame interval avg 4.72 / p95 8.4 ms with the streaming effects on vs 4.68 / 8.4 off, no long tasks. Keep animations in transforms/CSS or the shared canvas, never animate per character, and never put a live `backdrop-filter` over large streaming areas
- **Window background is shared** - params in `theme-core/effects` (`DEFAULT_BACKGROUND`: picture 15 %, panels 35 % theme tint, blur 10px, saturate 150 %, luminosity 10 %, 30 ms; the owner picked 0.35 / 10px / 150 % in the Codex playground), the layer and frosted-panel CSS in `renderer-runtime/background.ts`, hosts only wire selectors. 《彩云》 is committed once as `packages/renderer-runtime/assets/caiyun.webp`; the VSIX stages it in (`scripts/paths.js`), the CLI and the Codex++ user script inline it, the CDP overlay never does. Codex pictures travel through their own binding (`__woodfishCodexBackground`) and live in `%APPDATA%\Woodfish\backgrounds\`; VS Code copies them into globalStorage and loads `vscode-file://` URLs. In Codex never use a live `backdrop-filter` over the background: during a streaming reply it roughly doubled frame time (the running indicator, the caret and text scrolling under the composer recompute it every frame); the sidebar and composer draw a canvas-blurred static copy (`--woodfish-background-image-soft`, `background-attachment: fixed`). Bindings added with `Runtime.addBinding` are gone after a page reload; the watcher re-adds them on every load. VS Code 1.146's floating panels paint parts, panes, the grid frame and the editor card with `!important` (up to four classes), so the VS Code background rules are prefixed with `:root body`. A patched workbench only shows up after a full restart of the test VS Code, a reload can serve the old HTML
- **Codex autostart** - `woodfish codex autostart on` is a per-user logon task (`conhost --headless`, normal rights) running a private copy of the CLI as `codex daemon`; it only restarts a Codex that started without a port less than 90 s ago. From an elevated shell, `launch` relays the package launch through `explorer.exe`. When testing uninstall → restore on a real machine, restore by running `codex launch` from the installed copy in `%LOCALAPPDATA%\Woodfish`, never from a copy backed up in a snapshot folder: `codex watch` keeps running from wherever it was started, holds that temporary folder open, and deleting the worktree then stops halfway (happened in issues-8-1, 2026-11-14). After killing such a watcher, the logon daemon takes over the injection by itself
- **The AI install prompt is followed word for word** - `docs/agent-install.md` (structure copied from Obituary's) is what users paste to their agent, and the README sentence points at it on `main` (jsDelivr `@main` as the mirror), so a change to it needs `main` fast-forwarded. Keep it in step with the CLI: task `\Woodfish\Woodfish Codex` means installed (its Arguments between `--headless` and `codex daemon` are the installed command), `autostart on` first because it never touches Codex (exit 3 = risk text to show the user verbatim, `--accept-risk` only after they agree), then `launch` (exit 4 = ask before restarting); an agent running inside Codex never runs `launch` and asks the user to quit from the tray and reopen. Confirmed 2026-11-14: Windows PowerShell does not wait for `Code.exe` (a GUI program) run with `ELECTRON_RUN_AS_NODE=1` and loses its output and exit code unless the call is piped (`| Write-Output`); native UTF-8 output is garbled unless `[Console]::OutputEncoding` is UTF-8; `Get-FileHash` can be missing in a `powershell` started from Git Bash (use `sha256sum`); the daemon `autostart on` starts restarts a Codex opened less than 90 s ago at once, so the prompt waits until Codex has run two minutes. Tested on the owner's machine both ways: already installed (skipped, nothing changed) and `uninstall --keep-settings` → the VS Code route → task restored with `node woodfish.js codex autostart on` from `%LOCALAPPDATA%\Woodfish` (task XML byte-identical; the effects folder took the normal 8.1.1 upgrade)
- **Public text never says who made or chose something** - README, CHANGELOG, setting descriptions, CLI output and everything shipped into the user's effects folder (`effect.json`, `effect.js`, `README.md`) state what a thing does and its default, never who painted, made or tuned it or whose settings a default copies; “负责人”/“作者”/“the owner” belong in internal docs only. Exception: third-party permission notes such as the Bifrost button (decided 2026-11-14)
- **Woodfish Dark preset is the owner's own tuning** - the 5.x hand-written Bearded CSS, restored byte for byte. Never retune it or let the algorithm replace it; new presets follow its rules (start at the token color, turn forward on the hue circle to a more vivid end, 45°, pastel rainbow at 135° for the foreground)
- **Keep the VSIX small, no size limit** - the owner dropped the hard budget (2026-11-14): `pnpm package` prints the VSIX size and its biggest entries with their share, pre-publish only reports the source total. Compress what can be compressed without visible loss: 《彩云》 is a 2560px WebP at quality 70 (method 6; 232 → 177 KB, the same at 2x zoom), the icon a 256px JPEG at quality 90 with 4:2:0, the workbench bootstrap is whitespace/syntax-minified with names kept (tests look for constants by name), `out/extension.js` is fully minified. Bundled upstream theme JSON stays byte-for-byte upstream and the GPL text of the bearded theme must ship
- **README images are rendered and focused on the effect** - the owner wants every effect shown with its own picture in a list, never one long screenshot (2026-11-14; this replaced the old “code only” rule): the READMEs' 效果一览 / Effects at a glance table has one row per effect (picture + name + one sentence + how to turn it on or change it), the popular themes are a two-column grid. Code pictures come from `apps/vscode-extension/scripts/render-readme-images.js` (built bootstrap + `buildRuntimeCss`, code on the theme background plus the one widget a feature needs). The effect gallery and theme grid come from `scripts/promo/render-readme-effects.js` (`assets/readme/effects/`): the promo's stages and storyboard states with a still camera framed on the effect and no captions or badge; moving effects are 2.5–3 s animated WebP rendered at 60 Hz with every second frame kept, under ~1 MB each. Frame the effect itself: host UI that is its context is fine (the sidebar for the thread ring), unrelated window chrome, glow blobs, badges and slogans are not. The Codex settings page has no stand-in and is cropped from a real screenshot. Shots must render in time order (the pages' clocks only run forward). Rerun both scripts after changing gradients or effects
- **Promo video is rendered, not edited** - `apps/vscode-extension/scripts/promo/render-promo-video.js --bgm <music>` drives two headless Chromes frame by frame over CDP (`promo/cdp.js`, Node's built-in WebSocket) and pipes frames into ffmpeg: VS Code shots run the real bootstrap plus the effect plugins (`promo/stage.js`), Codex shots run the real `startCodexOverlay` and every shipped effect on a page with Codex's data-* hooks (`promo/codex-page.js`, `promo/codex-stage.js`). `promo/clock.js` replaces time, timers, rAF and `Math.random` in the pages, so renders are reproducible; 60 fps because the caret trail moves once per frame. Frames arrive as full-range BT.601 JPEG; encode them to limited-range BT.709 H.264 High 4.2 with a keyframe every 2 s (`startEncoder`), the default full-range level 5.0 stream stutters in Windows players. The owner wants effect shots framed on the effect (push in, follow), not the whole window: each page keeps one window size at 3× pixel ratio and the camera is the screenshot clip (Chrome re-rasterizes at the clip scale, so text stays sharp), following anchors the stages report; captions, the corner badge and the end card live in `promo/overlay-page.js`, counter-scaled to the clip. Every shot sits on 《彩云》 with the default background settings (the owner, 2026-11-14): VS Code shots use the extension's own background CSS (`runtimeCss(…, { backgroundImage })`), theme switches change only the colors, text over it goes on the frosted caption cards. `promo/storyboard.js` holds the scenes in BGM seconds on the measured beat grid; `--still <seconds>` writes single frames for review. Storyboard, BGM credit and license: `docs/internal/promo.md`. Output goes to the ignored `output/promo/`; clear old stills with `obit bury`, not `rm`
- **One Codex CLI, three distributions, one version** - npm (`woodfish`, built into `apps/cli/out/npm`; not published yet: npmjs.com showed “访问受限” to the owner on 2026-11-14, publish the current version once it is reachable), the GitHub Release (`woodfish.exe`, a Node 22 single executable built with `postject`, plus `woodfish.js` and `THIRD_PARTY_NOTICES-woodfish.md` in `out/release`) and the VSIX (`out/woodfish.js`, copied in by `scripts/bundle.js`; `package.js` fails without it) carry the same file, and the CLI's version is the extension's (`dist.js` refuses otherwise) so one tag carries all three. The extension runs it on the editor's own Electron (`process.execPath` + `ELECTRON_RUN_AS_NODE=1`, Node 22+ required, forks with older Node are told to use exe/npm); first use shows the CLI's own risk text in a modal (exit code 3), a running Codex is confirmed in a modal before `--yes` (exit code 4), and 启用 = `launch` + `autostart on`. Rules learned the hard way (2026-11-14): never start PowerShell with `-EncodedCommand` (Defender holds it 30 s+ when the unsigned exe starts it; `runPowerShell` uses a temp UTF-8-BOM `.ps1` with `-File`); the CLI deletes `ELECTRON_RUN_AS_NODE` at startup and only gives it back to its own children; the logon task and the shortcut run a private copy in `%LOCALAPPDATA%\Woodfish` (`woodfish.cmd` for the editor runtime, since tasks and shortcuts cannot set env vars); VS Code's updater terminates the editor-runtime daemon, so the extension restarts the task on activation. The CLI shares one copy of 《彩云》 between the CDP side and the Codex++ user script (`build.js` token), which keeps ~180 KB out of every distribution
- **Never take over the user's Codex shortcuts** - Woodfish does not modify, replace or delete Start menu, desktop or taskbar shortcuts to Codex (the owner asked, 2026-11-14). `woodfish codex shortcut` adds a separate “Woodfish Codex” entry (removed by `uninstall`). With autostart on, a Codex opened from the original shortcut is restarted with a port before its window shows: the daemon watches Codex's data folder while Codex is closed and wakes on its `lockfile` (~1.4 s to notice, killed at ~2.3 s; Codex needs ~7 s for its first window), measured in `docs/hosts/chatgpt-app.md`. Say this in every install description
- **README image links point at the release tag** - the extension is released from this branch, so `raw/HEAD` (main) lacks new images; use `raw/vX.Y.Z/…` and push the tag before publishing. `pre-publish-check.js` accepts HEAD or a version tag and checks the files exist. Between releases, a commit that only changes README text or external images (such as the contributor wall) may be fast-forwarded onto `main`, provided every README image link opens.
- **怀旧（5.x） is a code style, not a retune** - `woodfishTheme.overlay.style: classic` (preset 「怀旧（5.x）」, also used by 「霓虹全开」) adds what 6.0 dropped from the 5.x look: `font-weight: 700` and one `0 0 20px currentColor` halo scaled by `glow.intensity` (`overlay.ts`). Gradients and the cursor are already 5.x. Light themes keep the bright-tint glow (#31). The modern glow's gradient knobs (`overlay.hueShift` …) never reach the 5 built-in themes, so presets that only turn those knobs look unchanged there
- **Menu glass lives on `::before`** - a `backdrop-filter` on `.monaco-menu-container` or its scroll element makes it the containing block of the `position: fixed` submenu and clips it (#32, by Cralemon). VS Code 1.146 frosts menus itself the same way (`::before`, `--vscode-menu-background: transparent` on the container): keep its layer and tint, add only blur and grain. The editor context menu and the custom title bar menus are in a shadow root the injected CSS cannot reach; the activity bar's Manage menu is not (that is where to test submenus)

### JetBrains plugin maintenance

- The plugin (`io.github.woodfishhhh.woodfishtheme`, vendor Woodfish) has the 15 color themes and the gradient and glow overlay; since 8.2.0 it ships as `woodfish-theme-jetbrains-<version>.zip` on the GitHub Release (install through “Install Plugin from Disk…”) and, since 2026-11-21, on JetBrains Marketplace (plugin 36347, <https://plugins.jetbrains.com/plugin/36347-woodfish-theme>, vendor `Woodfish`, stable channel, MIT; 8.2.0 was uploaded by hand and sent for review, every later version is reviewed by hand too and is not public until approved, so READMEs offer both the Marketplace search and the zip). The Marketplace page (screenshots, license link → `apps/jetbrains/LICENSE` on `main`, docs/bug tracker links) is edited on the website, not in `plugin.xml`; it is the owner's own JetBrains account (sign in through its JetBrains Account button, not a new registration). `pluginVersion` in `apps/jetbrains/gradle.properties` is the extension's version (bump it with the other two). The Java side is a community contribution under its own `LICENSE`: change its behavior only deliberately, its tests must stay green.
- Build, test and compatibility from `apps/jetbrains` with JDK 21: `./gradlew test buildPlugin verifyPlugin` (zip in `build/distributions/`). `verifyPlugin` checks IC 2024.2 and 2024.3 by default; newer IDEs through `-Pide252LocalPath=<dir> -Pide262LocalPath=<dir>` (see `gradle.local.properties`), run it against the newest IDE before a release.
- Themes are generated, never hand-edited: `pnpm jetbrains:generate`, commit the result; `pnpm jetbrains:check` is the CI check (job `colors` in `.github/workflows/jetbrains.yml`, runs when `packages/theme-core`, `apps/vscode-extension/themes` or `apps/jetbrains` change). New token attributes go into `scripts/scopeMap.js` (row: attribute → VS Code scope stack); editor, console, diff, inlay and fold settings into `scripts/editorMap.js`. Every JetBrains name must be found in a real IDE: `python scripts/audit-keys.py --ide "<label>=<IDE dir>" … --keys <file> --out <tmp.json>` once per OS, then merge the new records into `scripts/verified-keys.json` by hand (`--keys` with `--merge` keeps only the listed keys, back the file up first); tests refuse unknown names.
- Colors follow VS Code, including its own defaults for what a theme leaves out (read from the workbench bundle, kept in `editorMap.js`). Plain code uses the `source` rule's color as JetBrains' `TEXT` (Woodfish Dark differs from `editor.foreground`), probe with the root scope `source`, not a language scope (One Dark Pro has a Java rule).
- Before a release, redo the screenshot comparison in `docs/hosts/jetbrains.md` ("验收方法") and rebuild `docs/hosts/jetbrains-colors.md`; only private X servers (WSL Xvfb, `unset WAYLAND_DISPLAY`) may open IDE windows, never the owner's desktop, and never `runIde` in CI. Pitfalls found while doing it: JetBrains' `options/*.xml` ignores unknown names silently (look names up in the IDE's class files), the Markdown plugin highlights a heading under the caret (park the caret on line 2), `pkill -f` kills the calling shell when the pattern is in its own command line (use `[x]` patterns), `( … ) &` inside `wsl.exe` dies with the call (use `nohup`), shell heredocs and tool arguments eat double backslashes (write regexes with the editor tools).

### Neovim colorscheme maintenance

- `apps/neovim` is the source of the public plugin repository `woodfishhhh/woodfish.nvim`. `pnpm nvim:sync -- <checkout>` replaces its `colors/` and `lua/` with the generated ones (pnpm 11 forwards the `--` to the script, `sync.mjs` skips it); edit nothing there by hand.
- Colors of languages come from VS Code itself: Shiki (vscode-textmate) colors `stats-samples/`, Neovim's Treesitter says which capture each character gets (`scripts/captures/`, committed), and the majority color and font style of every "capture + language" becomes `@capture.language`. Every language has its own `stats-samples/` file (`jsx` files are parsed by Neovim's `javascript` parser, so the jsx and javascript samples are counted together; `tsx` is separate); nothing copies another language. No custom Treesitter queries and no autocommands: a colorscheme must not change queries or highlights for other colorschemes.
- After changing a sample or the parser pins in `scripts/treesitter-sources.json`: `pnpm nvim:capture` (Neovim 0.11+, git, a C compiler; parsers are built under `%TEMP%/wf-neovim/ts`), `pnpm nvim:generate`, commit. After changing a palette or a VS Code theme file: `pnpm nvim:generate` only. `nvim:check` fails on stale captures too.
- `pnpm nvim:compare` renders every theme in Neovim (`:TOhtml`) and in Shiki, scores them and writes pictures and `report.md` (default `%TEMP%/wf-neovim`); run it on a clean tree, the report records the commit. It never opens a window: Neovim runs `--headless`, pictures come from headless Chrome/Edge. Judge a change by that report, not by the unit tests.
- Pitfalls: `nocombine` does not remove an inherited style (Neovim 0.12.6: with another highlight underneath it also loses the color), so an overlapping capture can leave an extra italic; groups with the same name as a capture in another language are untouched because only `@capture.language` is defined. Shell heredocs eat double backslashes, write regexes with the editor tools.
